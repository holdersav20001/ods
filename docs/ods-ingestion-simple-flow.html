ODS Ingestion - simple developer flow

The developer configures the dataset. The ODS platform handles orchestration, logging, lineage, reconciliation and retry safety.

DEVELOPER
Dataset config
Add or update YAML under patterns/<domain>/<dataset>.yaml.
Define keys, schema, topic, target table and source type.
developer owns: YAML, schema, target table
LANDING
Raw input arrives
File lands in S3, or API pull archives a JSONL batch to S3.
The platform registers the file and starts the pipeline.
platform writes: file_catalogue, run_log
PIPELINE
Validate and publish
Glue reads raw data, validates schema and DQ, writes curated data, then publishes to Kafka.
Non-canonical data is transformed before the sink.
platform writes: stages, offsets, lineage, recon
OUTPUT
Postgres and dashboard
Kafka Connect writes to Postgres. The dashboard shows status, counts, lineage and failures.
Successful runs are only closed after proof rows exist.
operator checks: dashboard and reconciliation
Written automatically
pipeline.file_catalogue pipeline.run_log pipeline.run_stage_log pipeline.lineage_edge pipeline.reconciliation_log pipeline.run_kafka_offsets pipeline.run_events

Platform contract for every ingestion

1 Create the run Open a traceable execution in run_log.
2 Write stages Record progress and failure points in run_stage_log.
3 Carry identity Propagate file_id, run_id and source metadata.
4 Capture offsets Store per-partition Kafka start/end ranges.
5 Write proof Add lineage edges and reconciliation checks.
6 Finalise last Only mark the run succeeded after proof rows exist.
RUN
One execution boundary

A run is the unit operators search for when they ask, "Did this load succeed?" Parent and child runs keep the end-to-end path queryable.

Example: parent s3_batch run with child ingestion, publish and optional canonicalize runs.
STAGE
A step inside a run

Stages show where work is currently running or where it failed. Each stage should start, then complete, fail, warn or skip.

Example: raw_read started, dq_check completed, kafka_publish failed.
FILE IDENTITY
The file is the anchor

The platform registers each landed batch in file_catalogue. Downstream jobs must carry the same file_id.

Example: file_id=dcebd... links raw S3, curated S3, Kafka messages and Postgres rows.
OFFSET
The Kafka message range

Offsets are not the business identity. They are the technical range that proves what Kafka messages were produced or consumed.

Example: partition 0 [120, 150), partition 1 [88, 103); total published = 45.
LINEAGE EDGE
A parent-to-child relationship

A lineage edge records that one thing created or contributed to another thing. This is how the viewer follows the chain.

Example: parent_file_id -> ingestion run, edge raw_to_curated, source S3 raw, target S3 curated.
RECONCILIATION
A count-based proof point

Reconciliation checks that records did not disappear or multiply across a boundary. Failures should stop final success.

Example: T0 checks curated rows == Kafka messages; T2 checks Kafka messages == Postgres rows.

What a dataset developer does

  • Create YAML with domain, dataset, source type, keys, schema and sink details.
  • Register schema if the topic uses schema-registry validation.
  • Create target table with required ODS metadata columns.
  • Provide a test input and check the dashboard after the run.

What the developer should not do

  • Do not manually insert rows into run_log or run_stage_log.
  • Do not invent lineage edges outside the approved pipeline flow.
  • Do not mark runs as succeeded from application code.
  • Do not rediscover files by date when file_id is available.
