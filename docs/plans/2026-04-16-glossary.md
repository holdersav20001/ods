# ODS Platform — Glossary and Terminology Reference

**Date:** 2026-04-16  
**Status:** Living document — update when new terms are introduced or canonical decisions change  
**Scope:** All four ingestion patterns and all shared platform components

---

## How to Use This Glossary

The canonical term for each concept is shown in **bold**. Where a document uses a variant that differs from the canonical form, that document should be updated to use the canonical term. If you are writing a new document, use only the canonical terms listed here. Acronyms are expanded in the table at the bottom of this document. When introducing an acronym for the first time in a document, write it out in full followed by the acronym in parentheses — on subsequent uses within that document, the acronym alone is sufficient.

## Platform Concepts

### B

**Business date**  
The calendar date that the data represents, as opposed to the date the data was processed. For example, a file containing claims submitted on 14 April 2026 has a business date of 2026-04-14 even if it is processed on 2026-04-15. Business date is extracted from the source filename using a pattern defined in the dataset YAML config and is used as the Parquet partition key and as a dimension in `pipeline.glue_job_log` queries.

### C

**crypto-shredding**  
A GDPR data erasure technique used for datasets containing personal data. Each data subject's records are encrypted with a unique per-entity Data Encryption Key (DEK). To erase a subject's data, the platform deletes their DEK from AWS KMS — the encrypted records become permanently unreadable without the key. This avoids the need to locate and delete individual records across S3 partitions and Kafka topic segments. See `2026-04-15-security-data-privacy.md` for the full design.

### D

**DAG** (Directed Acyclic Graph)  
The unit of work in Apache Airflow (MWAA). A DAG defines a set of tasks and the dependencies between them. Each pipeline stage in the ODS platform is implemented as one or more DAGs. Tasks within a DAG are individually retryable and observable in the MWAA UI.

**DAG 1**  
The MWAA DAG responsible for the first stage of the ingestion pipeline: transferring files from the SFTP server to S3 Raw using the `SFTPToS3Operator`. DAG 1 completes when the file is safely in S3 Raw; it does not perform ETL. On completion, it publishes an S3 Object Created event that triggers DAG 2 via EventBridge.

**DAG 2**  
The MWAA DAG responsible for the second stage of the ingestion pipeline: reading from S3 Raw, running the Glue ETL job (schema validation, DQ checks, CSV → Parquet conversion), and writing output to S3 Curated. DAG 2 is triggered by an EventBridge rule on S3 Raw Object Created events. It is independently retryable without re-running the SFTP transfer.

**`data_classification`**  
The four-tier data sensitivity classification applied to every dataset before it can be onboarded to the platform. Classification drives encryption, access control, and retention policy. The four tiers are:

- `public` — no access restrictions
- `internal` — Aviva staff only
- `confidential` — restricted to named teams; not for general internal circulation
- `restricted_pii` — contains personal data under GDPR; requires DPO sign-off and crypto-shredding plan

Classification is a blocking decision (D4) that must be completed before a dataset goes to production.

**DLQ resubmission**  
The manual process of replaying failed records through the pipeline from the S3 DLQ (`ods-dlq-{env}`). An engineer identifies the root cause of the failure, fixes it (in schema, DQ rules, source data, or pipeline config), copies the failed file to the appropriate source location, resets the `pipeline.file_state` or `pipeline.ingestion_file_state` record to `new`, and allows the pipeline to reprocess. Resubmission is intentionally manual — automated retry is not implemented because root cause must be understood before replay. See the failure-and-recovery documents for step-by-step procedures.

**DQDL** (AWS Glue Data Quality Definition Language)  
The rules language used to define data quality checks in AWS Glue. Rules are stored in versioned YAML config files per dataset and evaluated by the Glue ETL job. The platform uses two severity tiers: **hard block** (fails the job or routes the row to DLQ) and **soft warn** (emits a CloudWatch metric, row continues). DQDL is an AWS-proprietary language and is not portable to non-Glue environments.

### E

**EventBridge**  
AWS EventBridge is the event routing service used as the pipeline trigger mechanism throughout the ODS platform. It replaces Airflow S3 Sensor polling, which consumed a worker slot continuously and introduced polling-interval latency. EventBridge rules fire within milliseconds of an S3 Object Created event. Two rules are active in the ingestion pattern: one on S3 Raw (Raw Object Created → triggers DAG 2), and one on S3 Curated (Curated Object Created → triggers the publish DAG).

### F

**`file_catalogue`**  
A PostgreSQL table that serves as the Layer 1 idempotency whitelist for the ingestion pipeline. It contains approved file patterns (filename regex, domain, dataset, expected cadence) for every dataset registered on the platform. When DAG 1 receives a file from SFTP, it checks the `file_catalogue` before proceeding — files that do not match an approved pattern are quarantined to `ods-quarantine-{env}` and an alarm is raised. This prevents unrecognised or unexpected files from entering the pipeline.

### G

**Glue Schema Registry**  
The AWS-managed schema registry used by the ODS platform for all Kafka message schemas. It stores Avro and JSON schemas, enforces schema evolution compatibility rules (backward, forward, or full), and integrates natively with AWS Glue ETL jobs and MSK producers and consumers. The ODS platform does not use Confluent Schema Registry. Schema subject names follow the pattern `ods.{domain}.{dataset}`.

### I

**Ingestion pattern**  
One of four defined source integration patterns for the ODS platform. Each pattern describes how data moves from a specific source type into MSK. All four patterns share the same platform layer (Schema Registry, DLQ, PostgreSQL state store, audit topic, CloudWatch).

| # | Pattern | Status |
|---|---|---|
| 1 | S3 batch (SFTP → S3 Raw → Glue ETL → S3 Curated → MSK) | Designed; build starting |
| 2 | CDC → Kafka | In design |
| 3 | API → Kafka | Not started |
| 4 | Event → Kafka | Not started |

### M

**MWAA** (AWS Managed Workflows for Apache Airflow)  
The orchestration engine for all ODS pipelines. MWAA runs Airflow as a fully managed AWS service — no cluster to provision or maintain. All pipeline stages are implemented as Airflow DAGs. MWAA was chosen over AWS Step Functions for its observability (per-task status, retry, alerting) and its native `SFTPToS3Operator`. MWAA is not serverless — the environment incurs a base cost regardless of pipeline load.

### O

**`ods.pipeline.audit`**  
The shared Kafka topic to which all four ingestion patterns publish a structured audit event on every pipeline run (success and failure). The topic is sinked to `ods-audit-sink-{env}` via a Kafka Connect S3 Sink Connector for long-term retention and Athena queryability. It is the external-facing pipeline summary and complements (not replaces) `pipeline.glue_job_log`, which is the internal execution trail.

### P

**Publish DAG**  
The MWAA DAG responsible for the publish pipeline: reading a Parquet file from S3 Curated, running schema validation and DQ checks, publishing records to MSK with Kafka transactions, and writing an audit event to `ods.pipeline.audit`. The Publish DAG is triggered by an EventBridge rule on S3 Curated Object Created events. It is not numbered (unlike DAG 1 and DAG 2) because it is shared across all ingestion patterns.

### S

**S3 Curated Zone**  
The S3 bucket (`ods-curated-{env}`) that holds Parquet files produced by the Glue ETL job in the ingestion pipeline. It is the handoff point between the ingestion pipeline and the publish pipeline. Files in the Curated Zone are schema-validated, DQ-checked, and partitioned by business date. The presence of a new Parquet file in this zone is the trigger for the Publish DAG via EventBridge.

**S3 DLQ**  
The S3 bucket (`ods-dlq-{env}`) used as the Dead Letter Queue for failed or invalid records. The DLQ is partitioned by failure type, date, topic or dataset, and run ID:

```
ods-dlq-{env}/
  schema-incompatible/date={date}/topic={topic}/
  dq-dataset-failure/date={date}/topic={topic}/
  dq-row-failure/date={date}/topic={topic}/run_id={id}/
  count-mismatch/date={date}/topic={topic}/run_id={id}/
```

There is no automatic retry from the DLQ. All resubmission is engineer-driven. See DLQ resubmission above.

**S3 Raw Zone**  
The S3 bucket (`ods-raw-{env}`) that holds the original source files as received from the upstream system (CSV for the S3 batch pattern). Raw Zone files are never modified or deleted — it is a permanent archive of every file ever ingested. Full pipeline replay is always possible from Raw Zone without coordinating with the upstream source system.

### T

**T0 / T1 / T2 / T3**  
Reconciliation latency tiers — not business day offsets. Each tier represents a different check performed at a different cadence and latency:

| Tier | Check | Cadence |
|---|---|---|
| T0 | Publish-time count check: source row count vs Kafka offset delta | Synchronous, per pipeline run |
| T1 | Consumer lag monitoring: how far behind are consumers? | Continuous (CloudWatch MSK metrics) |
| T2 | Hourly count reconciliation: records in S3 Curated vs records in Kafka | Hourly |
| T3 | Daily full business reconciliation: end-of-day cross-system count and checksum verification | Daily |

See `2026-04-15-reconciliation-design.md` for the full design.
