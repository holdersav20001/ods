# Adversarial Audit A1 — SQL / migrations / functions / constraints

- **Date:** 2026-06-03
- **Scope:** `db/migrations/001`–`029_*.sql`, all live `cp.*` functions/views/triggers/constraints, `ods.*` target tables, `control/queries/trace_row.sql`.
- **Method:** EXPECTED derived from `docs/specs/`; every finding PROVEN against the **live** DB (`localhost:5440`, read-only `pg_get_functiondef` + `cp.*`/`ods.*` queries) plus migration `file:line` citations. CONFIRMED = reproduced on live schema/data; SUSPECTED = code path is wrong but no live trigger in committed demo data.
- **Live function count:** 27 `cp.*` functions, all bodies resolve against current schema (no orphaned column refs found; `lineage_edge_id`/`lineage_link` grep clean inside function bodies).

## Headline

The platform is **not** suffering from broken/stale function bodies — the SUPERSEDED re-declaration chain landed cleanly (028 won for the discovery selectors, 029 won for diagnostics/DLQ/contract; 002/015's stale copies are not the live copy). The real defects are **logic bugs inside the latest copies** and a **half-applied "output_link" rename** that left two parallel identity columns and an unmet spec contract.

| F1 | **P1** | `cp.get_schema_contract` "latest" ORDER BY | `029:680` (live) | **CONFIRMED** | The P3 "numeric semver" fix uses `nullif(regexp_replace(schema_version,'\D','','g'),'')::bigint`. It strips **all** non-digits and concatenates, so it is wrong for any version that is not a single trailing integer. Proven on live: `v1.10`→`110`, `v1.0`→`10`, `claim.v1.2`→`12`, `2026v1`→`20261`. Thus `v1.10` (110) > `v2` (2) and `v1.0` ties `v10`. "Latest contract" can resolve to the wrong row. Latent only because demo has a single `claim.v1`. | Sort on a proper version vector: `string_to_array(regexp_replace(schema_version,'^\D+',''),'.')::int[]` (or `regexp_split` per numeric group), not a digit-concatenation. |
| F2 | **P1** | Half-applied `output_link` rename | spec `2026-05-30-output-link-input-edge-rename.md` "Target Names"; live `cp.lineage_link`/`cp.lineage_edge` base tables, `cp.write_lineage_link`, `activate_target_visibility(... p_lineage_link_id ...)`; `ods.*._ods_lineage_link_id` **and** `_ods_output_link_id` | **CONFIRMED** | Spec mandates renaming the base table/columns/functions to `output_link`/`output_link_id`/`write_output_link`/`activate_target_visibility(... output_link_id ...)`. Worse: every target table carries **both** `_ods_lineage_link_id` and `_ods_output_link_id` (verified per table). The ground-truth reconcilers (`reconcile_sink`, `reconcile_sink_link`, `reconcile_workflow`) count rows via the **old** `_ods_lineage_link_id`, while `developer_diagnostics`/`dashboard_target_row_trace` require/join the **new** `_ods_output_link_id`. If any writer ever stamps one and not the other, recon and diagnostics diverge **silently**. | F3 | **P2** | `developer_diagnostics` → `active_visibility_conflict` GROUP BY | `029:314` (live) / dup `027:310`, `022:521` | **CONFIRMED** | The check groups active `ods.target_visibility` rows by `(domain,dataset,business_date,replacement_scope,replacement_key)` and flags `count(*)>1`. | F4 | **P2** | `cp.reconcile_workflow` terminal-run selector + accounting | `015:169` (live, NOT superseded) | **CONFIRMED (tiebreak) / SUSPECTED (double-count)** | (a) Picks the "terminal run" with `ORDER BY started_at DESC, run_id DESC` — a **clock + random-UUID** tiebreak. 028 explicitly migrated the discovery selectors to `seq DESC` (deterministic, monotonic) but reconcile_workflow was left on the legacy pattern — inconsistent and non-deterministic if two runs share `started_at`. (b) `v_dlq_out = sum(cp.dlq.record_count)` over **all** DLQ rows of the workflow **regardless of status**. A DLQ row that is later `replayed`/`resolved` (the demo row `c0f3a195…` is `status='resolved'`) feeds a corrected row into the sink, so it is counted in **both** `dlq_out` and `sink_out` → over-counts `accounted` and would report a spurious `double_count`/`breach`. | F7 | P3 | `cp.register_file` ON CONFLICT ignores path/state drift | `001`/live | **CONFIRMED (minor)** | Conflict key is `(file_md5,business_date,domain,dataset)`; on conflict it does a no-op `SET state=state` purely to fire RETURNING. ## Notes on things that are CORRECT (checked, not defects)

- **Edge-type trigger / `write_lineage_link` smuggling guard** (`trg_edge_type_matches_link`, `write_lineage_link` lines): both correctly force edge `edge_type` = link `edge_type` except annotation `'replay'`. Consistent with each other.
- **`edge_must_anchor` / `raw_edge_requires_source_file` / `upstream_link_required_for_run_edges` CHECKs** are internally consistent and the P1a 029 diagnostic fix now exempts exactly the same set (`orchestrates`,`quarantine`,`replay`) the anchor CHECK exempts — the previously-contradictory predicate is gone.
- **P2a contradictory predicate** (`_ods_workflow_run_id = $1 AND _ods_workflow_run_id IS NULL`) is **fixed** in the live `developer_diagnostics` (029): scoping is now via the output-link→run join, plus a separate table-wide `target_row_orphan_no_ods_ids` check. No longer a defect.
- **`recon_internally_consistent` CHECK** exactly matches the formula every reconcile fn computes (`discrepancy = source - accounted`, status⇔sign). No bypass found; `record_count`/`accounted_count` all have `>= 0` CHECKs.
- **`resolve_dlq` P2c terminal-traceability guard** is correct; it does not enforce the `open→under_review→…` ordering, but the spec calls that the "Preferred lifecycle" (not mandatory), so that is not a defect.
- **`dlq_status_enum`, `trigger_type_enum`, `status_enum` (run/stage)** all present and correct; negative-count and empty-`target_ref` writes are blocked by CHECKs (`target_ref_contract` requires non-empty path+content_hash+version).
