# A2 Audit — "Passes for the Wrong Reason" Test Review

**Auditor posture:** independent, adversarial. The existing suite is GUILTY until
proven innocent. Method: for each gate-relevant claim, ask whether the test
constructs the HARDEST case the requirement implies, or asserts on a shape the
HARNESS hand-produced. Where feasible the requirement is encoded as a probe in
`tests/test_audit_a2.py` and run.

- **Requirements:** `docs/specs/2026-05-29-control-plane-design-v2.md`,
  `docs/reviews/2026-05-29-lineage-link-decision.md`
- **Probe file:** `tests/test_audit_a2.py`
- **Probe result:** `2 failed, 3 passed` — the 2 failures CONFIRM a real hidden
  bug behind a weak test (merge per-slot misattribution).

---

## Headline finding

**`harness/fakes.py::fake_merge` misattributes per-slot record counts to the
WRONG upstream run, and NO existing test can catch it.**

`fake_merge` zips `slot_counts` (passed in FILE order: 10, 20, 30 — see
`harness/composers.py:78`) against `upstreams = runs.succeeded_runs(...)`
(`harness/fakes.py:235`, `zip(upstreams, slot_counts)` at line 283).
`succeeded_runs` is documented **newest-first** (`control/runs.py:90`), so the
discovered order is reversed relative to file order. Result (proven empirically):

| input_slot | upstream_run named | edge.record_count | upstream's REAL ingested count |
|---|---|---|---|
| 0 | newest run (file with 30 rows) | **10** | **30**  ← mismatch |
| 1 | middle run (20 rows) | 20 | 20 |
| 2 | oldest run (file with 10 rows) | **30** | **10**  ← mismatch |

The merge link total (60) and recon (60==60) still balance because a sum is
order-invariant. Every existing merge test asserts only **multisets / sums**, so
all stay green while the per-slot provenance is wrong. This is the exact
fan-out failure pattern: the test and the code share the hidden assumption that
"as long as the multiset of counts matches, the binding is right."

Probe `test_audit_merge_slot_count_binds_to_correct_upstream` **FAILS**, proving
the bug. (Whether the *fix* is in `fake_merge` zip order or in re-deriving counts
per discovered upstream is a code question — out of scope for this audit-only
pass.)

### System-level recon note (QA-flagged class, confirmed)
`control/recon.py` + `cp.write_reconciliation_check` only compute
`discrepancy = source_count − accounted_count`, and BOTH operands are PASSED IN by
the caller. No recon path independently derives `accounted_count` from the lineage
graph or the actual target-row count. Therefore the recon LAYER cannot detect a
real imbalance where a stage wrote fewer rows than it claimed — it only checks the
caller's own arithmetic. The recon tests reflect this honestly (the breach/double
cases test the formula), but no test asserts `accounted_count` against ground truth
(e.g. `count(ods.orders)` for the link). This is a coverage gap, not a test that
lies, but it is the same family the fan-out crutch belonged to.
