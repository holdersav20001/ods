# Audit A3 — Spec-vs-Itself Contradiction Audit

**Date:** 2026-05-30
**Auditor:** A3 (independent) — internal contradiction audit of the shipped ODS control plane.
**Branch:** `feat/p6-adversarial-audit` · **DB:** `ods_cp` (schema 001–009 APPLIED, not modified).
**Scope:** cross-check requirements (spec v2, lineage-link decision C1–C4, plan gates) against the
mechanisms that implement/constrain them (migrations 001–009, `control/`, `harness/`, `trace_row.sql`,
deployed `pg_proc` signatures).
**Posture:** audit only — nothing fixed. The original worst bug (dedup key vs fan-out, both on one page,
never cross-checked) is the template; this audit hunts for every *other* instance of the same class.

---

## Headline

**`cp.run_output_link(run_id, edge_type)` re-introduces the exact "never per run" defect that C1 / decision-#6
exist to kill — at the *discovery* layer instead of the *storage* layer.** The C2/009 dedup key was widened so a
run can mint K links for one `edge_type` (fan-out). But the function the harness uses to *find* an upstream
output, `run_output_link`, collapses those K links back to ONE (`ORDER BY created_at DESC … LIMIT 1`). For a
multi-output upstream `edge_type` (canonical_to_sink fan-out, or any future multi-output run-to-run hop), the
disambiguator C3 added (`upstream_lineage_link_id`) is fed a value that is *not* disambiguated — silently the
newest sibling. The schema can now represent K outputs; the discovery API cannot address them.

- **CONFIRMED contradictions:** 4
- **Spec-appendix drifts vs deployed functions:** 1 (plus 1 self-contradiction *inside* the spec — see C-2)
- **Doc-drift / stylistic (non-blocking):** 3

---

## CONFIRMED contradictions

### C-1 (HIGH) — `run_output_link` returns one link per (run, edge_type); C1 says a run has K outputs per edge_type

**Requirement.**
Decision-#6 / C1 invariant, spec v2 §"User decisions" line 35–42:
> "One link per output, never per run … A run that produces K outputs mints **K links**; `run_id` is **never**
> the implied output id … Fan-out of identical canonical bytes to two sinks produces **two** `canonical_to_sink`
> links."

C3 (decision doc §3) requires run-to-run edges to name the **exact** upstream output via
`upstream_lineage_link_id`, "so a consumer of one output of a multi-output upstream run does **not** over-claim."

**Mechanism (conflicting).**
`db/migrations/009_lineage_link_hardening.sql` (d) and deployed `cp.run_output_link`:
```sql
CREATE OR REPLACE FUNCTION cp.run_output_link(p_run_id uuid, p_edge_type text)
RETURNS uuid LANGUAGE sql STABLE AS $$
    SELECT lineage_link_id FROM cp.lineage_link
    WHERE consumer_run_id = p_run_id AND edge_type = p_edge_type
    ORDER BY created_at DESC, lineage_link_id DESC LIMIT 1;
$$;
```
`control/runs.py:75-82` documents it returns "the **newest** such `lineage_link_id`". This is the **only**
sanctioned way the harness discovers an exact upstream output — `harness/fakes.py:140,276,367`,
`harness/composers.py:265`.

**Why they can't both hold.** `run_output_link` keys on `(run_id, edge_type)` — precisely the per-run grain
C1/C2 declared insufficient. When an upstream run produced K>1 links of that `edge_type` (the fan-out case the
spec *mandates*, line 41–42 and test line 247), `run_output_link` returns one arbitrarily (newest), discarding
the rest. The downstream `upstream_lineage_link_id` is then set to that single newest link — which is C3's exact
over-claim/under-name hazard, just relocated from the view to the discovery query. The system can *store* K
outputs but cannot *address* the non-newest ones; C1's "never per run" is violated at the API boundary.

**Why it passes today (the trap).** No fake calls `run_output_link` for a fan-out `edge_type`. The two sinks are
`canonical_to_sink` *terminal* outputs — nothing downstream discovers them — and every `run_output_link`
callsite happens to target a single-output edge (`raw_to_curated`, or a single `merge`/`canonical`). So the
contradiction is **latent**: the first run-to-run hop that consumes a multi-output upstream `edge_type` (e.g. a
future "sink → downstream" or a canonicalize that reads a fanned-out curated output) silently loses lineage. This
is the same "passes because the input that would break it is never supplied" pattern as the original dedup bug.

**Severity:** HIGH (correctness; latent but guaranteed to bite once a multi-output run-to-run hop exists).
**Fix (mechanism):** `run_output_link` must not exist as a `(run, edge_type)→one-link` function. Either (a) make
it return `SETOF uuid` and force callers to disambiguate by target identity (sink_type/path/content_hash), or
(b) add a `run_output_link(run_id, edge_type, sink_type, path)` overload that names the exact output. The spec
appendix should then carry that signature and the LINEAGE GATE should add: "discovering an upstream of a
multi-output edge_type names the exact output, not the newest." Do **not** fix by spec-softening — C1 is the
load-bearing invariant.

### C-2 (MEDIUM, spec-internal) — Decision-#5 quotes the OLD 3-part dedup key that decision-#6 / 009 explicitly replaced

**Requirement A.** Spec v2 decision-#5, lines 25–27 (restart-task idempotency):
> "`write_lineage_link` dedups on `(consumer_run_id, edge_type, target_ref->>'content_hash')` → re-running an
> unchanged task produces the **same link**."

**Requirement B (same document).** Spec v2 decision-#6, lines 38–40 + appendix lines 164–167 + schema table
line 92:
> "the link dedup/uniqueness key carries **output identity** — `(consumer_run_id, edge_type,
> COALESCE(sink_type,''), COALESCE(target_ref->>'path',''), COALESCE(target_ref->>'content_hash',''))`."

**Mechanism (authoritative).** Deployed `uq_lineage_link_target` and 009 `write_lineage_link` ON CONFLICT use the
**5-part** key. The 3-part key is the *exact* defect 009 was written to remove.

**Why they can't both hold.** The same spec states the dedup key two ways, one paragraph apart. Decision-#5's
3-part key is the original fan-out-collapsing bug verbatim; decision-#6 corrects it. A reader/operator who trusts
decision-#5 (e.g. reasoning about whether two restart-task writes dedup) will compute the wrong answer for any
`canonical_to_sink` write (where `sink_type`/`path` now participate). This is a doc self-contradiction of the
*precise variety the original bug was* — two requirements on adjacent pages, never cross-checked.

**Severity:** MEDIUM (doc-only; deployed code is correct, but the spec contradicts itself on its most defect-prone
key). **Fix (spec):** edit decision-#5 line 26–27 to quote the 5-part hardened key (or reference decision-#6
instead of restating). The restart-task idempotency *claim* still holds under the 5-part key (same input + same
target ⇒ same 5 components ⇒ same link), so only the quoted key string is wrong.

### C-3 (MEDIUM) — Function appendix `register_file` ON CONFLICT comment vs deployed behavior on `domain/dataset` change

**Requirement.** Appendix line 147:
> "ON CONFLICT (file_md5, business_date) DO UPDATE state -> returns existing file_id (idempotent)."

Decision-#5 line 25 restates: "`register_file` dedups on `(file_md5, business_date)`."

**Mechanism.** Deployed `register_file(p_s3_raw_path, p_file_md5, p_business_date, p_domain, p_dataset)` keys
idempotency on `(file_md5, business_date)` only — `domain`/`dataset`/`s3_raw_path` are **not** in the conflict
key. (Confirmed: 5-arg signature, the appendix's own key.)

**Why this is a latent contradiction.** The *signature* drift is resolved (appendix and deployed both 5-arg, no
`p_workflow_run_id` — good, P5 fixed that). But the key `(file_md5, business_date)` means: the **same MD5 on the
same business_date but a different `domain`/`dataset`** dedups to the *first* file's `file_id` and silently
ignores the new domain/dataset (the appendix says "DO UPDATE state", i.e. it updates state but keeps the old
domain/dataset row). The spec nowhere states this cross-dataset collision is intended or impossible. It is a
requirement (uniqueness grain) enforced by a mechanism whose grain the spec never reconciles against the
multi-dataset reality the schema otherwise supports (`domain,dataset` are real columns). Flagging as a
*requirement-with-undocumented-grain*, not a hard code bug.

**Severity:** MEDIUM (correctness IF MD5 collisions across datasets are possible; otherwise doc-gap).
**Fix (spec + maybe mechanism):** state explicitly whether `(file_md5, business_date)` is globally unique or
should include `(domain, dataset)`. If cross-dataset same-MD5 files are possible, the key must widen; if not, the
spec must assert the invariant. Empirically probeable — see `tests/test_audit_a3.py::audit_a3_register_file_*`.

### C-4 (LOW→MEDIUM) — "Provenance walk is rows-complete" / "trace every row to raw" vs the write-event grain caveat

**Requirement A.** Decision-#3 line 19 and DLQ test line 264: "Provenance walk is **rows-complete**." LINEAGE
GATE item 1 (plan line 34): "for **every** target/curated row produced this hop, `cp.v_provenance` returns a
`raw_to_curated` ancestor. **Zero orphans.**" Spec test line 245: "trace one `ods` row → raw."

**Requirement B (caveat).** Decision doc §6 "Open caveats": "lineage is **write-event grain**, not **row grain**.
A merged row traces to all N inputs collectively, not 'which input.'"

**Why they tension.** "Rows-complete" / "trace every row to raw" / "trace one ods row → raw" all use **row**
language; the grain caveat says the model is **write-event** grain and explicitly **cannot** answer per-row
provenance for a merge ("traces to all N inputs collectively"). The two are reconcilable (every row reaches *a*
raw ancestor set; you just can't pick *which* input a given merged row came from) — but the spec never states the
reconciliation, and a reader of GATE item 1 / decision-#3 will over-read "rows-complete" as row-grain. The merge
test (line 246) only asserts `SUM(edge.record_count) == link.record_count`, i.e. **count** reconciliation —
consistent with write-event grain, *inconsistent* with the "trace one row" phrasing taken literally.

**Severity:** LOW→MEDIUM (no code defect; a claim that, read literally, promises more than the model delivers).
**Fix (spec):** qualify "rows-complete" → "write-event-complete (every write-event traces to raw; per-row
attribution within a merge is out of scope — see grain caveat)." Make GATE item 1 say "every row's *link*" not
"every row."

## STYLISTIC / doc-drift (non-blocking, no contradiction)

- **S-1.** `v_provenance` SELECT list exposes `upstream_run_id` but **not** `upstream_lineage_link_id`
  (deployed viewdef). `trace_row.sql` therefore re-reads `lineage_edge` directly to recurse — and its header
  *documents* this ("v_provenance does not expose upstream_lineage_link_id … so we read it from
  cp.lineage_edge"). Consistent and intentional, but the recursion key being hidden from the public view is a
  smell: two queries (the view and trace_row) independently encode the link→link walk. If one is edited and the
  other isn't, they drift. Not a contradiction today (both walk link→link via `upstream_lineage_link_id`).
- **S-2.** Schema table line 92 calls `lineage_link` "1 link per write-event, **N per run**" while the same row's
  PK comment elsewhere says "1 link per output." "Write-event" and "output" are used interchangeably; harmless
  but worth pinning one term.
- **S-3.** Appendix `start_run` note (line 136–137) says trigger_type `'orchestrates'` writes an orchestration
  edge, but the `edge_type` seed (line 110) and decisions use `'orchestrates'` as an *edge_type* while
  `trigger_type` enum (line 131) is `'airflow'|'manual'|'replay'|'dlq_drain'` — `'orchestrates'` is **not** a
  valid `trigger_type`. The appendix conflates the trigger_type value with the edge_type name. Doc bug, not a
  deployed-code contradiction (no function checks `trigger_type='orchestrates'` against the enum). Worth a
  one-word fix.

## Cross-checks that PASSED (no contradiction found)

- **Deployed function signatures vs appendix:** all 12 `cp.*` functions match the appendix arg lists and return
  types (register_file 5-arg, write_lineage_link 7-arg, run_output_link/succeeded_runs present). The P5 drift
  the contract test was meant to stop is **closed** at the signature level. (The residual issues are *semantic*
  — C-1, C-3 — not signature drift.)
- **C2 dedup key vs fan-out:** the original headline bug is genuinely fixed — 5-part key with COALESCE; fan-out
  of identical bytes to two sinks mints two links (different `sink_type`/`path`); non-sink links still dedup
  (COALESCE folds NULLs). Decision-#5 restart-task idempotency composes correctly with the 5-part key.
- **`upstream_link_required_for_run_edges` CHECK** matches the run-to-run edge set
  (`curated_to_canonical`/`merge_to_canonical`/`canonical_to_sink`) named in C3 and the schema table.
- **v_provenance link→link rewrite vs trace_row.sql vs GATE:** all three walk `upstream_lineage_link_id`
  (link adjacency) post-009; consistent. CYCLE key is `lineage_link_id` in both the view and the schema note.
- **decision-#4 overwrite-mutability vs decision-#5 restart vs C2:** they compose. Old links pin to logged bytes;
  changed content under a live run mints a new link (ON CONFLICT misses on content_hash) and is **not**
  auto-superseded — the boundary rule (lines 47–52) and the 5-part key agree.

## Empirically testable

C-1 and C-3 are probeable. A minimal probe is added at `tests/test_audit_a3.py`
(`conn` rollback fixture, `audit_a3_*` namespace, cleanup in `finally`, schema never dropped):
- `audit_a3_run_output_link_collapses_fanout`: write two `canonical_to_sink` links for one run (distinct
  sink_type), assert `run_output_link(run,'canonical_to_sink')` returns only one — demonstrating C-1.
- `audit_a3_register_file_cross_dataset_collision`: register same `(file_md5, business_date)` under two
  different `(domain, dataset)` pairs; assert the second returns the first's `file_id` (domain/dataset ignored)
  — demonstrating C-3's grain gap.

C-2 and C-4 are pure document contradictions (no probe).
