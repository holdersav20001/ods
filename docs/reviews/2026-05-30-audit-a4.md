## Headline findings

### S1 — Multi-output, SAME edge_type: discovery picks a sibling by random UUID (CONFIRMED DEFECT, High)

**Spec requirement.** Decision doc C1: a `lineage_link` is *"the id of one output / one write-event, never a per-run id… once a single run can produce multiple outputs, anything that identifies an output by run_id (or by a key that omits output identity) loses or corrupts lineage."* P5/009 fixed the **documented** fan-out (two `canonical_to_sink` links disambiguated by `sink_type`). This audit stresses the **undocumented** variant: one run emits **two `raw_to_curated` outputs** — same `edge_type`, **no `sink_type`** to disambiguate.

**Over-claim / under-reach.** Downstream stages discover their upstream output via `cp.run_output_link(run_id, edge_type)`:

```sql
SELECT lineage_link_id FROM cp.lineage_link
WHERE consumer_run_id = p_run_id AND edge_type = p_edge_type
ORDER BY created_at DESC, lineage_link_id DESC LIMIT 1;
```

The key is **only `(run_id, edge_type)`** — it omits output identity, exactly the C1 hazard. Tiebreak evidence:
- `cp.lineage_link.created_at` defaults to **`now()`** (transaction-start time), *not* `clock_timestamp()`. Two outputs written in one transaction get the **identical** `created_at` (probe asserts `cas[0]==cas[1]`).
- The remaining tiebreak is `lineage_link_id DESC` — a **random `gen_random_uuid()`**.

So `run_output_link` returns whichever sibling wins a **random UUID compare**, and there is **no API to name the other**. A downstream `curated_to_canonical` / `merge` / `sink` edge wired this way:
- **OVER-CLAIMS** the UUID-picked sibling's raw file (it traces to a raw it may not have consumed), and
- **UNDER-REACHES** the intended output (unaddressable via discovery).

**Evidence.** `test_s1_multioutput_same_edgetype_DEFECT_nondeterministic_discovery` (both links share `created_at`; picked == `max(la,lb)` by UUID), and `test_s1_downstream_traces_to_wrong_sibling_DEFECT` (a real `curated_to_canonical` wired via `run_output_link` traces to exactly the UUID-picked raw; the sibling is excluded).

**Why existing tests miss it.** Every shipped multi-output case uses *different* discriminators (fan-out uses `sink_type`; merge uses *different upstream runs*). No test exercises one run with **two outputs of the same edge_type and no sink_type**. The harness never produces this shape, so discovery's ambiguity is never surfaced.

**Fix (not applied).** Either (a) make downstream discovery name the exact output by content (target path/hash), not by `(run, edge_type)`; or (b) forbid a run from emitting >1 output of a non-fan-out `edge_type`; or (c) at minimum make the tiebreak deterministic *and meaningful* (e.g. `created_at` → `clock_timestamp()` plus an explicit output selector passed by the caller). UUID-DESC is neither deterministic-across-runs nor semantic.

### S7a — Cycle guard protects the view but NOT `trace_row.sql` (CONFIRMED DEFECT, Medium-High)

**Spec requirement.** 006/009: the provenance walk *"MUST terminate instead of an infinite loop"* on a malformed/adversarial replay edge that closes a cycle. The spec's row-trace operation is *"trace one ods row → raw via v_provenance"*, implemented by `control/queries/trace_row.sql`.

**Finding (split).** With a forged self-cycle (`lineage_edge.upstream_lineage_link_id` repointed at its own link — the 009 CHECK only requires non-null, it does **not** forbid a cycle):
- `cp.v_provenance` **HOLDS** — the 009 `CYCLE lineage_link_id SET is_cycle` clause flags the revisited row (`is_cycle=true`) and terminates (probe sees 2 rows, one `is_cycle`).
- **`control/queries/trace_row.sql` HANGS** — it runs its **own** `WITH RECURSIVE chain` that recurses on `upstream_lineage_link_id` **with no `CYCLE` clause**. The same forged edge loops until `statement_timeout` (`QueryCanceled`).

**Impact.** The query the spec designates for trace-to-raw is unguarded. A single malformed/adversarial provenance edge (the replay hop is the first cross-execution edge writer — exactly the case 006 was gated for) **hangs trace-to-raw** — an availability under-reach. The view's guard gives false assurance.

**Evidence.** `test_s7a_cycle_view_safe_but_trace_row_DEFECT_hangs`: asserts `is_cycle` present in the view, then `pytest.raises(QueryCanceled)` on `trace_row.sql` under a 3 s timeout (savepoint-isolated).

**Fix (not applied).** Add a `CYCLE lineage_link_id SET is_cycle USING path` (or a `hop`/visited guard) to the `WITH RECURSIVE chain` in `trace_row.sql`, mirroring the view; or have `trace_row.sql` drive entirely off `cp.v_provenance` (which is already guarded) instead of re-walking `cp.lineage_edge`.

## Scenarios that HELD (regression-guarded by the probes)

### S2 — Refeed, no cross-contamination (PASS) + ordering fragility (NOTE, Medium)
Committed original→sink, then `replay_single_file` with a corrected file under a **new** `workflow_run_id`. The old sink link is immutable and still traces to **only** the old raw; the replay chain traces to the **corrected** raw and discovery anchors to the replay ingest run (`test_s2_refeed_no_cross_contamination`).
**Caveat (NOTE).** The guarantee relies on the corrected ingest committing with a **strictly newer `finished_at`**. `latest_succeeded_run`/`run_output_link` order by `finished_at DESC` then a **random run_id**. `test_s2_refeed_discovery_ordering_fragility_NOTE` forces an exact `finished_at` tie and shows discovery is decided by `run_id DESC`, not recency — a tie (clock collision, or a backfilled/out-of-order `finished_at`) can re-canonicalize the **stale** ingest, silently cross-contaminating. Same root cause as S1 (discovery keyed on time+UUID, not identity). The shipped X5 test sidesteps this by committing between executions.

### S3 — Double replay idempotent (PASS)
Two replays of the same corrected file: original recon **unchanged** (QA H1); each replay canonical traces to the corrected raw **exactly once** (single raw leaf — `trace_row.sql`'s `DISTINCT` collapses fan-in, no over-claim/dup).

### S4 — Concurrent writers, one workflow_run_id (PASS)
Two canonicalize-shaped writers on two connections, same `workflow_run_id`, discovering the same ingest upstream, committed together: exactly **2 distinct** links (none lost, none duped), and **each branch independently traces to raw**.

### S5 — Merge with a failed slot (PASS for merge; system UNDER-REACH NOTE, Medium)
3 files arrive (10+20+30); the third **ingest fails** (no link, status `failed`). `succeeded_runs` discovers **only the 2 succeeded** slots; the merge link's `SUM(edge.record_count)==record_count==source==accounted==30`, status `ok`, **2 slots** (no phantom slot for the failed ingest). Per-slot recon is internally correct — **merge H5 holds** (`test_s5_merge_failed_slot_recon`, PART A).
**UNDER-REACH (NOTE).** The failed ingest's **30 rows are accounted by NO recon row anywhere** (PART B asserts `0` recon rows for the failed run). There is no end-to-end check comparing *files-arrived* (60) to *rows-reaching-canonical* (30); a wholly-failed upstream's rows silently vanish from reconciliation. This is arguably outside merge's H5 scope ("does not decide completeness — orchestrator's job"), but it is a real gap in the *system's* recon coverage: recon never breaches on a fully-failed upstream.

### S6 — DLQ + trace, forced imbalance (PASS)
Forced `good+dlq=18 < source=20` (2 rows lost without quarantine): the quarantine link is **reachable in `cp.v_provenance`** (rows-complete, decision 3), recon **breaches** (`discrepancy=2`, status `breach`) — non-vacuous, catches a *real* imbalance, not the self-consistent balanced fake. Quarantine edge is not `canonical_to_sink`, so it never inflates the good sink count. The `>source` side is also covered (`double_count`, `test_s6_double_count_detected`).

### S7b — Deep chain still fully traces (PASS)
A legitimate 5-hop chain (raw→curated→4×canonical) traces fully to raw (`raws == {s3://raw/deep}`, `max hop ≥ 5`) — the `CYCLE` clause does **not** truncate real lineage.
