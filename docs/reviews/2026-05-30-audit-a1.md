**Auditor:** independent A1 lens (assume more bugs of the P5 fan-out-dedup class).
**Date:** 2026-05-30  **Branch:** `feat/p6-adversarial-audit`
**Authoritative requirements:** `docs/specs/2026-05-29-control-plane-design-v2.md` (decisions #1–#6,

**Probes:** `tests/test_audit_a1.py` (9 probes, all green: 4 `CONFIRMED` pin a real defect, 5 `SOUND`

---

## Headline

**`cp.run_output_link` re-introduces the exact input-side over-claim that C3/009 was created to kill,
the moment an upstream run is legitimately multi-output — and which output it picks is decided by a
random UUID.** This is the same *class* as the P5 fan-out bug (a key/selector that silently collapses
or mis-selects among multiple valid outputs of one run), surviving on the output→input boundary.

**CONFIRMED bug count: 4** (1 High, 2 Medium, 1 Low). **`run_output_link` multi-output case: YES — a
real wiring hazard, see A1-1.**

---

## A1-1 — `run_output_link` silently mis-wires a multi-output upstream  **[CONFIRMED · HIGH]**

**Mechanism:** `cp.run_output_link(run_id, edge_type)` (009 §d) returns
`ORDER BY created_at DESC, lineage_link_id DESC LIMIT 1`. The harness uses the return value *verbatim*
as the consumer edge's `upstream_lineage_link_id` (`harness/fakes.py:140, 276, 367`).

**Spec violated:** C1 invariant — "a run that produces K outputs mints **K** links; `run_id` is
**never** the implied output id." C3 — a run-to-run edge must name the **EXACT** upstream output. The
whole point of 009 was that a consumer of one output of a multi-output run must not mis-name/over-claim
its siblings. `run_output_link` collapses the run's K outputs back to **one**, chosen for the consumer
arbitrarily — defeating C3 at the discovery layer.

**Evidence (CONFIRMED):**
- `test_probe_CONFIRMED_run_output_link_collapses_multioutput` — one ingestion run mints two distinct
  `raw_to_curated` links; `run_output_link` can only ever surface one; the other is **un-nameable** as
  an upstream through this API.
- `test_probe_CONFIRMED_run_output_link_tiebreak_is_nondeterministic` + live check
  (`SELECT now() <> clock_timestamp()` → **false**): every link written in one transaction shares
  `created_at` (txn-stable `now()`), so the `created_at DESC` order is a **tie**; the winner is decided
  by `lineage_link_id DESC` — a random `gen_random_uuid()`.
- Live end-to-end demonstration: the **same** two-output scenario, run twice, had `run_output_link`
  pick output **A** the first time and output **B** the second. The consumer's
  `upstream_lineage_link_id` (hence its trace-to-raw) flips between identical runs.

**Why it's not theoretical:** the spec's own boundary rule (decision #5/#6) and A1-4 below both create
multi-output runs: a mid-run clear-task with changed content mints a *second* link under the same run;
fan-out mints two `canonical_to_sink` links; two transform_versions mint two canonical outputs. In all
of these, every downstream `latest_succeeded_run` + `run_output_link` discovery wires to a coin-flip
output. `fake_sink` (`:367`) does exactly this for `curated_to_canonical`/`merge_to_canonical`.

**Concrete fix:** `run_output_link` must not exist as a 1-row selector once K>1 is legal. Either (a)
make discovery return the *set* of output links and require the caller to disambiguate by the target it
actually read (path/content_hash/transform_version), or (b) add a discovery primitive
`run_output_link_for_target(run_id, edge_type, content_hash|path)` and have the harness/real jobs pass
the specific output identity they consumed. Failing that, a `UNIQUE(consumer_run_id, edge_type)` partial
constraint where K=1 is intended would at least make the silent multi-output case loud. The 1-row
`ORDER BY ... LIMIT 1` must be removed from any path that feeds `upstream_lineage_link_id`.

## A1-2 — `COALESCE('')` collapses two distinct hashless+pathless outputs  **[CONFIRMED · MEDIUM]**

**Mechanism:** the hardened key (009 §b) is
`(consumer_run_id, edge_type, COALESCE(sink_type,''), COALESCE(path,''), COALESCE(content_hash,''))`.
COALESCE was added so NULL parts dedup non-sink links (NULLs are otherwise distinct in a unique index).
But it also means two **genuinely distinct** outputs of one run that BOTH omit `path` and `content_hash`
fold to the identical key `(run, edge, '', '', '')` and collapse — **and the second output's edges are
silently dropped** (the idempotent-replay branch reuses the link and never inserts the new edges).

**Spec violated:** C1 — K outputs ⇒ K links. The 009 comment claims COALESCE only "folds NULL parts so
non-sink links still dedup"; it does not acknowledge that it *also* over-folds two distinct
hash/path-less outputs into one.

**Evidence (CONFIRMED):** `test_probe_CONFIRMED_two_hashless_outputs_collapse` — two `raw_to_curated`
outputs with no `content_hash` and no `path` return the **same** `lineage_link_id`, and the link ends
with **1** edge (the second write's edge silently dropped). Control:
`test_probe_SOUND_distinct_path_disambiguates_hashless` confirms a distinct `path` alone *does*
disambiguate — so the hole is specifically the both-absent case.

**Why it's reachable:** the spec makes `target_ref` `{path, content_hash, version}` but does **not**
make path/content_hash NOT NULL, and `write_lineage_link` accepts any `target_ref` jsonb. Any real
producer that emits two partitions/outputs without a per-output hash (or a stubbed early integration)
silently loses the second. The harness only avoids this by convention.

**Concrete fix:** require output identity to be non-empty for multi-output-capable edge types — e.g. a
CHECK that `COALESCE(target_ref->>'content_hash', target_ref->>'path')` is NOT NULL, or carry an
explicit `target_ref->>'output_id'` (the decision doc's own "Or" option) and key on it. At minimum,
`write_lineage_link` should RAISE rather than silently dedup when an existing link is hit but the new
edge set differs (see A1-4).

## A1-3 — `register_file` silently discards the second path on md5 collision  **[CONFIRMED · LOW]**

**Mechanism:** `cp.register_file` (002) does `ON CONFLICT (file_md5, business_date) DO UPDATE SET
state = state` — a no-op. A second registration with the **same** `(md5, business_date)` but a
**different** `s3_raw_path` returns the existing `file_id` and **keeps the first path**; the second
path is discarded.

**Spec context:** decision #5 / file_catalogue "dedups across runs" on `(file_md5, business_date)`.
Dedup is intended. The defect is the *silent loss of the differing path*: any run that believes it read
the second physical location has its provenance pinned (via `source_file_id`) to the **first** path.

**Evidence (CONFIRMED):** `test_probe_CONFIRMED_register_file_drops_second_path` — registering
`locationA` then `locationB` under one md5 yields one `file_id` whose stored `s3_raw_path` is
`locationA`.

**Severity rationale (Low):** identical md5 normally ⇒ identical bytes, so a path difference is rare
(re-delivery to a new prefix, or a true md5 collision). But when it happens it is undetectable — no
error, no flag. **Fix:** either treat a differing path under the same md5 as a conflict to surface
(RAISE or record it in a `paths[]` array / `also_seen_at`), or document that path is not authoritative
and provenance must not present `s3_raw_path` as the unique source location.

## A1-4 — Idempotent-replay branch silently drops a CHANGED edge set  **[CONFIRMED · MEDIUM]**

**Mechanism:** `write_lineage_link`'s `IF v_link IS NULL` branch (009 §c) keys dedup **only** on
`(run, edge, sink, path, hash)`. On a hit it returns the existing link and **skips the edge-insert loop
entirely** — it never checks whether the supplied `p_edges` match the edges already stored.

**Spec violated:** decision #5 says re-running an **unchanged** task is idempotent. It does not license
silently discarding a **changed** provenance set under an unchanged target. A mid-run clear-task that
adds a merge slot, or a corrected upstream discovery, produces the same target identity but a different
(larger/different) edge set; that change is dropped with no error, leaving stale lineage.

**Evidence (CONFIRMED):** `test_probe_CONFIRMED_replay_with_changed_edges_silently_dropped` — second
call with the same target but **two** edges (one new upstream file) returns the same link and the link
still has **1** edge.

**Concrete fix:** on a dedup hit, compare the incoming edge set to the stored one; if they differ,
RAISE (genuine conflict — the target identity should have changed if provenance changed) rather than
silently no-op. This is the input-side analogue of why C2 added output identity to the key.

## Mechanisms probed and found SOUND (break-attempts that failed)

- **Quarantine identity (post-I1):** `cp.quarantine` sets `content_hash = dlq_id` (unique). Two
  quarantine events in one run with the **same** `payload_ref` mint **two** links — no collapse.
  (`test_probe_SOUND_two_quarantines_same_payload_distinct`.) A quarantine link and a non-sink
  provenance link in the same run with the same `path` also coexist (edge_type differs in the key).
  (`test_probe_SOUND_quarantine_does_not_collide_with_canonical`.)
- **Path-only disambiguation:** two hashless outputs with distinct `path` do NOT collapse — the key's
  `path` component works. (`test_probe_SOUND_distinct_path_disambiguates_hashless`.)
- **Changed-content boundary (decision #6):** a re-write with a new `content_hash` mints a new link and
  both persist (the stale link is not auto-superseded — the spec's own acknowledged operational gap,
  not a key defect). (`test_probe_SOUND_changed_content_mints_new_link_but_leaves_stale`.)

## Cross-cutting structural note (SUSPECTED)

`cp.lineage_edge` has **no uniqueness constraint** (only a PK on its own random `lineage_edge_id` —
verified via `pg_constraint`). All dedup protection lives in `write_lineage_link`'s application logic;
the moment any path inserts edges outside that function (or the dedup branch is bypassed as in A1-4),
duplicate edges under a link are possible and would corrupt recon counts and provenance fan-in. Not
independently exploitable through the sanctioned API today, so SUSPECTED — but it means the integrity
of every count rests entirely on one function, with no DB backstop.
