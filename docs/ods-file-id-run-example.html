ODS Ingestion - carrying file_id through a true run

A concrete example of one file, the run rows it creates, and the identity each job must carry.

Main rule The file_id created when the file is registered is the identity of the batch. Every job receives that exact value as a parameter and writes it into its run, lineage, Kafka messages and sink rows.
1. REGISTER
File lands in S3
policies_20260507.csv
The platform registers the file once and assigns file_id.
creates: file_id=F-001
2. INIT RUN
Airflow creates the run set
One parent run plus child runs for ingestion and publish.
All rows use the same file_id.
creates: R-PARENT, R-INGEST, R-PUBLISH
3. INGEST
Raw to curated
Glue receives --file_id F-001 and reads the raw file.
It writes curated Parquet and a lineage edge.
writes: raw_to_curated
4. PUBLISH
Curated to Kafka
Glue receives the same --file_id F-001.
Kafka messages carry _ods_file_id=F-001.
writes: offsets + curated_to_kafka
5. SINK
Kafka to Postgres
Sink rows retain _ods_file_id and _ods_run_id.
Operators can join back to every run and stage.
queries by: _ods_file_id=F-001

Example table rows for this file

Table Important row What must match Why it matters
file_catalogue file_id=F-001, domain=insurance, dataset=policies, business_date=2026-05-07, state=sunk F-001 This is the root identity for the landed batch.
run_log R-PARENT, pipeline_type=s3_batch, file_id=F-001, status=succeeded F-001 Parent row gives the end-to-end operator status.
run_log R-INGEST, pipeline_type=ingestion, file_id=F-001, parents=[R-PARENT orchestrates] F-001 Ingestion child proves the raw file became curated data.
run_log R-PUBLISH, pipeline_type=publish, file_id=F-001, parents=[R-PARENT orchestrates] F-001 Publish child proves curated data became Kafka messages.
lineage_edge child_run_id=R-INGEST, parent_file_id=F-001, edge_type=raw_to_curated F-001 Viewer can start from the file and find the curated output.
lineage_edge child_run_id=R-PUBLISH, parent_file_id=F-001, edge_type=curated_to_kafka F-001 Viewer can continue from curated data to Kafka.
run_kafka_offsets run_id=R-PUBLISH, topic=ods.insurance.policies, partition=0, start=120, end=150 R-PUBLISH Proves the exact Kafka range written by the publish run.
Postgres target policy_id=P1001, _ods_file_id=F-001, _ods_run_id=R-PUBLISH F-001 Consumers can trace a sink row back to the file and run.

What the job must receive

Job Required identity parameters
ods_ingestion.py --run_id R-INGEST, --parent_run_id R-PARENT, --file_id F-001
ods_s3_publish.py --run_id R-PUBLISH, --parent_run_id R-PARENT, --file_id F-001
ods_canonicalize.py --run_id R-CANON, --parent_run_id R-PUBLISH, --file_id F-001

What the records must carry

Where Metadata fields
Kafka message _ods_file_id=F-001, _ods_run_id=R-PUBLISH, _ods_domain=insurance, _ods_dataset=policies
Canonical message Keep _ods_file_id; change only shape/business payload.
Postgres row _ods_file_id, _ods_run_id, _ods_business_date, _ods_ingested_at
Bad smell: if a downstream job has to rediscover the file using only domain, dataset and business_date, the chain is already weaker. Pass the explicit file_id instead. Date-level lookups can attach the run to the wrong file when two files share the same business date or a replay happens.

Legend - example labels used in this diagram

F-001 Example pipeline.file_catalogue.file_id. In production this is a UUID such as dcebd612-....
R-PARENT Example parent run_log.run_id for the end-to-end s3_batch run.
R-INGEST Example child run_log.run_id for the ingestion job.
R-PUBLISH Example child run_log.run_id for the publish job.
R-CANON Example child run_log.run_id for canonicalize; only present when is_canonical=false.

For non-canonical datasets, add a canonicalize child run after publish. It still carries the same file_id, but its parent is the publish run because it consumes the raw Kafka range produced by publish.
